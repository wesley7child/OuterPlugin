# VOIDIOV 功能文档

## 目标与适用范围

本技能用于 VOIDIOV 任一业务项目、公共资料目录或跨项目功能的文档建设。它服务于用户使用、开发维护、故障排查和验收，不把项目概览、接口清单或源码注释当成功能文档。

适用场景包括：

- 新功能先建立可验收的设计契约，再随实现更新文档。
- 存量功能按当前代码、配置、SQL、任务和协议反向还原真实行为。
- 审查已有文档，发现重复、冲突、失效路径、无证据结论或过度承诺。
- 整理单项目与跨项目文档的归属、索引、覆盖矩阵和验证边界。

本技能是公共技能，不预设项目数量、项目名称、目录名称、网关名称、技术栈或调用拓扑。所有具体边界必须从当前工作区规则和实际证据读取。不要把某次任务中的项目名、路径、端口、服务关系或历史结论写成技能级固定规则。

本技能不替代根目录或子项目的 AGENTS.md、.cursor/rules/*、README、数据库规则和安全规定；发生冲突时遵循更具体且当前生效的规则。

## 核心原则

1. 当前实现优先。README、旧设计和历史文档只能作为线索，与源码、配置或 SQL 冲突时必须记录差异并以当前证据为准。
2. 一个用户目标或系统责任边界对应一份详细功能文档。紧密子操作可以合并，互不相关的能力必须拆分。
3. 同一事实只保留一份详细权威说明。其他位置保留导航、项目差异或索引，不维护相互漂移的副本。
4. 证据和状态分开。源码存在不等于运行成功；已实现不等于已验证；静态核查不等于部署、联调、性能或真实数据验收。
5. 保留长期有用的边界。删除重复背景、逐行源码和无关清单，但保留字段、状态、权限、错误、事务、并发、兼容和验收事实。
6. 遵循最小变更。不要因为文档合并删除源码、注释、唯一实现说明或仍被引用的文件；必要时将旧文件改为短导航，并先检查引用。
7. 未知写“待核查”，不适用写“无”并说明原因，不用概括性措辞掩盖缺口。
8. 数据库结构变更、外部写入、真实账号、设备密钥、生产服务和推送发布都遵循当前项目授权；文档任务本身不扩大执行权限。

## 文档深度

按风险和可独立验收程度选择深度：

- A 级：跨项目调用、认证/会话、权限、数据库写入、外部 HTTP、Socket/消息、定时或启动任务、并发/租约、缓存一致性、敏感数据、发布/迁移/回滚或核心用户状态。
- B 级：单项目但包含多个实现层、持久化、后台任务、复杂页面流程或明确用户操作。
- C 级：局部文案、简单样式、单文件修复或不改变行为的重构，登记在所属功能文档或变更记录中。

A/B 级需要独立正文和证据；C 级不强行拆文档。已有同主题文档时优先更新，而不是新建重复文件。

## 执行流程

### 1. 读取规则和确定工作区

修改前按实际路径读取：

- 工作区根规则和任务涉及的子项目规则。
- README、文档索引、覆盖矩阵、已有专题和旧入口。
- 调用方与被调用方的路径常量、配置、入口、数据规则和协议定义。

先确认当前工作区是否存在公共资料目录或独立文档仓库。不要假定固定名称；如果用户没有要求创建公共仓库，不要自动创建。

### 2. 划定边界和功能清单

记录：

- 用户、管理员、客户端、任务、事件或 Socket 从哪里进入。
- 功能目标、非目标、涉及项目、责任方和数据边界。
- 是否需要跨项目同步、权限、发布顺序、协议兼容或人工迁移。
- 候选功能属于已文档化、待文档化、仅内部能力还是历史未暴露入口。

从 Controller/Route/Handler、页面菜单、任务入口、启动流程、事件/消息/Socket、配置开关、数据库用例和 README 盘点，不按目录名或类名猜测功能。没有业务 API 的表、配置和内部工具也必须归入某份文档或明确标记“仅初始化/未暴露”。

### 3. 反向核查实现链路

至少追踪：

入口/触发 -> 参数校验与归一化 -> Application/Service -> Domain/规则 -> Repository/Mapper/外部适配 -> 响应或异步结果

同时核对：

- Request/Response、事件、Socket 或协议字段的类型、必填、默认值、范围、归一化和兼容性。
- 状态集合、状态转换、禁止转换、不变量和副作用。
- 表、字段、唯一键、索引、写入时机、事务边界、重复提交、竞态、多实例、重启和补偿。
- 配置键、来源、默认值、覆盖优先级、超时、重试、资源上限和失败回退。
- 鉴权、角色、跨服务信任、敏感信息、日志脱敏和审计。
- 输入错误、业务冲突、权限拒绝、上游错误、传输失败、持久化失败、调度失败和空数据的处理。

无法从当前证据确认的内容写“待核查”或“部署待验证”，不得写成当前实现。

### 4. 确定文档归属并收敛重复

优先采用当前项目已有目录和命名。若工作区存在公共资料仓库：

- 公共文档负责整体架构、跨项目调用链、公共契约、联调、部署、排障和端到端验收。
- 项目文档负责本项目的 API、字段、SQL、配置、算法、页面操作和本地开发。
- 公共文档只摘录影响协作的字段和状态，详细实现链接回生产方文档。
- 跨项目功能改变时同步更新正文、索引、覆盖矩阵和受影响项目入口。

若没有公共资料仓库，仍按“跨项目权威说明与项目内部说明分层”的原则组织，不为了套用固定目录复制整套文档。

### 5. 编写或更新正文

用户手册放在前面，开发和验收信息放在后面。A/B 级文档至少覆盖：

1. 用户/调用方入口、前置条件、操作步骤、成功结果和常见失败处理。
2. 背景、目标、非目标、适用角色和责任边界。
3. 设计契约与当前实现；没有设计稿时明确写“由当前实现反向核查”。
4. 入口到结果的调用链、同步/异步行为、关键分支和状态转换。
5. 请求/响应、事件或协议字段表，必要时引用生产方完整说明。
6. 数据对象、表/字段/索引、事务、并发、幂等、重试、恢复和人工 SQL 边界。
7. 配置、权限、敏感信息、日志、超时、资源上限和兼容性。
8. 故障决策表：触发条件、是否写状态、是否回滚、是否重试、下一步处理。
9. 可执行验收矩阵、实际验证结果、未验证风险和变更记录。
10. 证据矩阵，将关键结论映射到真实路径、类/方法、配置键、表/索引、日志或命令。

后台任务、启动流程和内部 API 没有用户页面时，写触发条件、调用方、运维步骤、成功判据和失败恢复，不虚构用户操作。

### 6. 更新索引和覆盖矩阵

项目文档索引至少列出功能名称、入口、状态、链接和最后核查日期。跨项目或从零盘点时保留覆盖矩阵，至少列出：

| 入口/触发 | 所属功能文档 | 参与项目或模块 | 证据完整度 | 当前状态 | 未验证风险 |
| --- | --- | --- | --- | --- | --- |

稳定 API、配置、权限键、协议字段或表结构改变时，同步检查生产方、消费方、文档和兼容性影响。

### 7. 收口验证

按实际范围执行：

- Markdown 相对链接、源码证据路径、索引覆盖和重复旧链接检查。
- 文件命名、编码、空链接、敏感信息和凭据扫描。
- 文档变更的 git diff --check。
- 修改代码时运行涉及项目的最小编译或测试；只修改文档时不启动业务服务、不连接生产数据库、不执行任务。
- 只有实际执行并记录命令、环境、日期和结果，才使用 [测试] 或“已验证”。

## 推荐文档结构

可按复杂度合并章节，但不要省略适用事实：

    # 功能名称

    > 状态：已实现 / 已验证 / 部分实现 / 待核查
    > 所属项目或公共资料：...
    > 最后核查：YYYY-MM-DD
    > 证据状态：源码 / 配置 / SQL / 测试 / 部署待验证

    ## 用户使用或运维入口
    ## 目标、非目标与责任边界
    ## 设计契约与当前实现
    ## 调用链、字段与状态
    ## 数据、配置、权限与安全
    ## 故障、并发、重试与恢复
    ## 验收与证据
    ## 变更记录

索引、项目概览、覆盖矩阵和治理文档可以采用各自现有格式；固定入口名和现有外部引用优先保持稳定。

## 命名和目录

遵循当前项目规则。若项目采用本技能推荐的 doc/ 约定：

- Markdown 功能文件使用 中文名称-english-name.md，英文部分使用小写单数和短横线。
- 索引使用 文档索引-readme.md，项目概览使用 项目概览-project-overview.md，覆盖矩阵使用 覆盖矩阵-coverage-matrix.md。
- user/、api/、background/、system/ 等目录名可按项目现有约定使用。
- 已被引用的文件名不要单独改名；改名必须同步所有链接、索引和变更记录。

若项目已有不同命名规则，以更具体的项目规则为准，不为了统一技能而重命名无关文件。

## 状态和证据语义

推荐使用：

- 草稿：信息仍在调研或方案未确认。
- 设计确认：契约已确认，尚未完成实现。
- 开发中：实现进行中。
- 已实现：代码或配置已落地，但验证未完成。
- 已验证：本轮有可复核测试或真实环境证据。
- 部分实现：明确列出占位、缺失分支或未接通链路。
- 已废弃：由新方案替代并链接替代来源。

证据标记：

- [源码]：入口、Application、Domain、Mapper、配置类或注解中的事实。
- [配置]：配置文件、环境变量或部署配置中的事实。
- [SQL]：初始化脚本、Mapper、迁移文件或明确的人工 SQL。
- [测试]：本轮实际执行的编译、单测、接口测试或真实环境检查。
- [部署待验证]：依赖外部服务、数据库、网络、证书、账号、设备、性能或生产环境。

“已实现”不等于“已验证”。外部联调、性能容量、权限部署、数据迁移或真实行情未执行时，必须单列待验证边界。

## 精炼和质量门禁

提交前逐项确认：

- 用户或运维能够只看前置章节完成一次正常操作，并知道至少三类适用失败的处理方式。
- 开发者能够从证据矩阵找到入口、用例、规则、持久化/外部适配和配置来源。
- 字段表覆盖影响调用、存储、权限、状态、兼容或排障的字段；完整 DTO、SQL 和源码通过链接引用。
- 状态/故障表说明触发条件、副作用、回滚、重试和恢复；不适用项明确写“无”。
- 关键结论都有证据；设计意图、历史行为、当前实现和后续事项分开。
- 文档只保留影响使用、实现、维护、排障、安全或验收的事实。
- 索引、覆盖矩阵、项目文档和公共文档之间没有明显冲突。
- 链接、命名、敏感信息扫描和适用的 diff/测试检查已经完成。

## 参考资源

- 新建或重写功能文档时，读取 references/document-template.md。
- 盘点功能、审查实现链路或判断遗漏时，读取 references/document-review-checklist.md。
- 需要确定 A/B/C 深度、设计/实现双状态或故障语义时，读取 references/document-depth-guide.md。

只读取当前任务需要的参考资源，不要把参考文件全文复制到功能文档。

## 交付说明

最终回复用中文，简要说明：

- 新增、更新、导航化或保留的文档，以及唯一权威来源。
- 功能覆盖范围、当前状态和关键源码/配置/SQL 证据。
- 已执行的链接、命名、敏感信息、diff、编译或测试检查。
- 未完成的部署、数据库、联调、性能或生产验证边界。

不要把未执行的测试写成通过，也不要因为文档整理而声称业务实现已经改变。
